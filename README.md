### 멤버 , 영화 , 예약 , 상영 , 상영관은 각각 고유한 id 를 갖는다.

데이터베이스의 관점에서 볼 때 관계를 구성

### 1. 영화

한 영화는 여러 상영을 할 수 있음
영화와 상영은 1:N 관계

### 2. 상영관

상영관은 여러 상영을 할 수 있음
상영관과 상영은 1:N 관계

### 3. 멤버

멤버는 여러 예매를 할 수 있음
멤버와 예약은 1:N 관계

### 4. 상영

상영 정보는 여러 예매와 연결됨
상영과 예약은 1:N 관계

### 따라서 각각의 객체는 자신만의 고유한 id 를 가지고있고 관계를 맺는 foreign key 를 가짐으로써 서로의 관계를 식별한다.


## 구현해야할 기능

1. 각각 객체 클래스를 생성 및 고유 키와 외래 키 속성 부여
2. 데이터 베이스 확장 가능성을 위한 인터페이스 저장소 및 Memory 상을 통한 구현
3. 할인 정책 구현
4. 예약 서비스 구현
5. 결제 서비스 구현
6. 사용자를 위한 주문 서비스 구현

## 문제점

1. 관계의 무결성에 대한 검토
- 한 사람이 같은 영화를 여러번 예매하는 것 이외에도 영화를 상영했을 때 시간이 겹치거나 상영 객체가 가지고 있는 예약 상태가 제대로 관리 되도록 해야함

2. 시간
- LocalDateTime 을 사용하였지만 실제 사용을 대비해 조금 더 엄격한 기준과 조건을 설정해야함
- 서로 다른 시간의 비교, 겹치는 시간의 비교 정의, 상영관 자체의 운영 시간에 따른 영화 상영가능상태 검사 등

3. 속성
- Member 는 실제로 사용해야 하므로 비밀번호 , 이름 , 주소와 같은 추가적인 내용이 필요함
- 고유한 id 를 어떤식으로 관리할지 결정해야함
- 상영 클래스는 오직 상영에 집중해야하는데 그 상영에 있는 예약상태를 스스로 괸라하고 있음

4. 인터페이스와 구현체
- Repository 관리가 내가 짠 코드가 최선인가?
- 특정 인스턴스를 저장할 때 시간에 따른 조건을 추가해볼 수 있을거 같음
- 주문 서비스는 예약서비스와 결제 서비스에 의존하고 있음

5. 테스트 케이스
- 전체적으로 테스트 케이스는 맞고 틀리고에 중점을 두고 있음
- 최대한 많은 상황에 대해 구현해서 예기치 못한 에러에 대비해야 함
- 특정 케이스를 위한 예외클래스(ex: 상영관이 운영을 하지 않는 상태에서 상영을 시작하는 경우) 가 필요해 보임
